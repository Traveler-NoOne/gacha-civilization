## 一、设计目标

解决 **4X 类游戏教程难做**的问题。

传统任务系统的矛盾：**任务本质是引导，但一旦配上奖励，就变成胁迫**。玩家不想按预设路线走，但奖励摆在那里，不拿难受；拿了，又得走一条自己不想走的路。

本作的任务系统**不承担"强制教程"功能**（教程由**日志系统与手册**承担）。任务系统只提供**可选的引导路径**和**统一的奖励池**，让不同熟悉程度的玩家都能**按自己的节奏获取全部奖励**。

---

## 二、三阶段结构

每个任务系列划分为三个阶段，自上而下为：

| 层级 | 含义 |
| --- | --- |
| **终极挑战** | 该系列的最终目标，代表玩家已完全掌握对应模块 |
| **阶段性成果** | 终极挑战的拆解，代表玩家掌握了某个子模块或里程碑 |
| **链式任务** | 阶段性成果的进一步拆解，代表具体的引导步骤，供新手逐步跟随 |

**层级关系：终极挑战 → 若干阶段性成果 → 若干链式任务。**

---

## 三、奖励池规则

整条任务系列**共享一个统一奖励池**。奖励池 = 该系列所有任务奖励的总和，**总量固定，不因领取方式而改变**。

**三种领取入口：**

| 玩家类型 | 完成方式 | 领取内容 |
| --- | --- | --- |
| 新手 | 逐条完成链式任务 | 逐条领取对应奖励 |
| 老鸟 | 直接完成阶段性成果 | 该阶段性成果 + 旗下所有链式任务的奖励 |
| 究极老鸟 | 直接完成终极挑战 | 该终极挑战下所有**未领取**的奖励，一次性全部领取 |

**无论走哪条路径，最终获得的总奖励量完全一致。** 区别只在于领取节奏：分批到账、打包到账、还是一次性清空。

---

## 四、三种玩家的体验

- **新手**：不懂就跟着链式任务走，一步一步来，奖励**分批到账**，维持动力。
- **老鸟**：对系统有基本理解，但不想做详细引导。直接完成阶段性成果，跳掉繁琐步骤，**提前拿到该模块的全部奖励**。
- **究极老鸟**：完全不需要引导，直接按自己的节奏打终极挑战，**一次性拿走整条线的奖励**。也可以为了某个特定奖励，**选择性地**完成某一条链式任务或阶段性成果。

---

## 五、经济平衡说明

奖励池的总量，从设计之初就是按"**完成终极挑战**"的标准来定的。能完成终极挑战的玩家，意味着他已经熟悉核心系统、具备相应能力、达到了该阶段应有的水平。他一次性领走全部奖励，是他应得的，**不存在"跳过任务导致经济失衡"的问题**。

链式任务的分批领取，只是把这个固定总量**拆开**，让新手可以提前拿到一部分，维持动力。老鸟和究极老鸟的跳级领取，只是改变了**到账节奏**，没有改变总量。

因此，任务系统不会破坏经济平衡。**奖励的分配逻辑跟着"能力证明"走，而不是跟着"流程完成度"走。**

---

## 六、与整体设计理念的一致性

这个设计与 [终局-成长模式](./终局-成长模式.md) 的「**成长按钮主动权在玩家手里**」是同一逻辑：**游戏不逼玩家做任何事，只给不同入口。玩家选哪个入口，决定的是体验节奏，不是收益多少。**

> 新手被引导但**不被绑架**，老鸟被尊重但**不被特殊对待**，究极老鸟被信任但**不被奖励惩罚**。三种玩家，同一个奖励池，没有谁吃亏，也没有谁占便宜。

---

## 七、奖励池领取窗口

跳级完成阶段性成果或终极挑战时，玩家会**一次性解锁大量奖励**。如果这些奖励直接入账，很可能**超出存储上限**，导致溢出浪费。为解决这个问题，奖励池的领取**通过一个独立的奖励窗口进行，奖励不会自动发放，而是由玩家手动领取**。

**窗口规则：**

- 所有奖励**默认显示为暗色 + 小锁图标**，代表尚未解锁。
- 当玩家完成某个任务（链式任务 / 阶段性成果 / 终极挑战），对应奖励的**小锁图标消失、图标变亮，并立刻排列到奖励列表最前边**，代表可以领取。
- 玩家**点击奖励图标**后，该奖励才正式发放到账。
- 奖励领取的**先后顺序由玩家自己决定**，不强制一次性全部领取。

**设计目的：**

- 防止跳级领取时因一次性入账过多而**超出存储上限，造成溢出浪费**。
- 让玩家自己控制领取节奏，根据自己的仓储情况和当前需求，决定先领什么、后领什么。
- **暗色 + 小锁 → 亮起 → 排列到最前**的视觉反馈，让"解锁"这件事本身有明确的正反馈，玩家一眼就能看到自己刚刚解锁了什么。

---

## 八、补充说明

- 任务系统**不替代教程**。教程功能由**日志系统与手册**承担，任务系统只提供可选的引导路径。
- **终极挑战的完成条件必须是硬性状态检测，无法被误触发**，确保奖励不会被错误发放。
- 该结构可应用于**主线任务、系统引导、科技树解锁**等多个场景，作为**通用的任务框架**。

## 九、与现有系统的关系（依赖分析）

### 现状

| 项 | 现状（证据） |
| --- | --- |
| 任务数据 | 全在 `GameState.state`：`task_groups`（组/文件夹）、`tasks`（进行中）、`tasks_done`（档案）、`_group_open`（折叠态）、`enemy_killed`（击杀计数）—— `game_state.gd:78-82` |
| 单任务字段 | `{id, name, desc, group, goals[{type,key,need,text}], reset_cycles, system, created_cycle}`；归档另写 `done_cycle`、`archived`（`task_page.gd:401-410`） |
| 系统任务 | `system:true` 标记、不可删；`_setup_default_tasks()` 建 2 组（`sys_main` 主线进程 / `sys_world` 世界经营）+ **4 个**系统任务 —— `game_state.gd:1904-1933` |
| 目标类型 | **只有 5 种**：`item`（收集图鉴物品）/ `resource`（累计资源）/ `kill`（击杀）/ `tile`（占领地块）/ `cycle`（存活周期）—— `task_page.gd:366-372` |
| 完成检测 | **拉取式（poll），无状态钩子**：`_goal_progress()` 现算（`task_page.gd:281-295`）、`_is_complete()` 全部 `progress>=need`（`:234-241`）；只在 `refresh()` / `on_cycle_finished()` 时重算（`:94`、`:528-529`） |
| **奖励** | **完全没有**。任务结构里无 reward 字段；**全项目没有"发放 / 领取奖励"函数**（grep `reward/奖励/claim/领取/发放` 仅命中注释与无关项） |
| 教程 | **没有任何教程机制**。只有一个死变量 `state["tutorial_skipped"]=true`（`game_state.gd:83`，无人读写）；「手册」页是**名词/世界观设定集**（`TermDB`），**不是教程**；唯一提示通道是 `GameState.toast` |
| 日志页结构 | 日志不是一级页，被包进浮窗 `LogPanel`（`log_panel.gd`，右上角书本按钮 `game_screen.gd:347-355`）；四子页 `SUB_TABS` = 任务/记录/图鉴/手册（`log_view.gd:5-10`） |
| 存储上限 | `storage_cap()`（`game_state.gd:116-126`）：生产力 `PRODUCTION_STORE_CAP`=20（`constants.gd:129`）、科研 `RESEARCH_STORE_CAP`=200（`:135`）、具体资源 `STORAGE_CAP_CONCRETE`=100（`:137`）+ 仓储加成 `warehouse_bonus()`（`game_state.gd:130-136`，每级 50） |
| 超上限处理 | **静默夹取（clamp）**：`add_res()` 超 cap 直接写 cap（`game_state.gd:105-112`）；**只有**"周期生产力盈余"那一条路径是**作废**（`:1591-1600`） |

> ⚠️ **关键依据（正好支持 §七）**：普通 `add_res` 是**静默夹取**——一次性大额奖励会被**无声削到上限**。所以"独立领取窗口 + 手动逐个领"不只是仪式感，而是**真的能避免溢出浪费**。

### 需要新增

1. **任务层级字段**（终极挑战 / 阶段性成果 / 链式任务）与**奖励池数据结构**（挂在 `state` 里，参照 `tasks/tasks_done` 与 `_setup_default_tasks()`）。
2. **条件型（硬状态）目标类型** —— 现有目标全是"计数器 ≥ need"，**没有布尔硬状态**。可复用现成的 `tech_unlocked()`（`game_state.gd:438`）、`has_flag()`（`:442`）思路。
3. **一条绕过夹取的"待领奖励"入账路径** —— 默认 `add_res` 会夹取，奖励窗口需要"先解锁、后手动发放"的两段式。
4. **奖励领取窗口** —— 首选 `DialogLayer` + `UIKit.dialog()`（`ui_kit.gd:349`）；**现成模板**是作弊菜单的"滚动长内容"做法（`game_screen.gd:738-742`），正适合"列一批奖励 + 逐个领取"。数据挂点与弹窗框架都现成。

### 挂载点提醒

- 弹窗：`UIKit.dialog()/confirm()`（`ui_kit.gd:349/357`）+ `game_screen.open_dialog/close_dialog`（`game_screen.gd:745-754`），Esc 关闭（`:769-775`）。
- ⚠️ `game_screen._on_toast()` 是**空实现**（`game_screen.gd:385-386`）——真 toast 在 `main.gd:17,45-63`，注入时别接错地方。

## 十、待定问题（落地前必须拍板）

1. **数据形态**：是给现有 `tasks` 加 `tier / parent / rewards` 字段，还是**另开一份"任务系列"数据**（现有扁平 `groups+tasks` 与三层层级差别很大）？
2. **硬状态目标要支持哪些**？现有 5 种目标全是计数器；"终极挑战必须硬性检测"意味着要新增条件型目标（科技解锁 / 建筑存在 / 占领指定地块 / 击败指定敌人 …）——需要一份目标类型清单。
3. **防重复 / 防漏领**：老鸟做完阶段性成果后再回头做链式任务怎么办？"该系列已领多少、还剩多少未领"要有账本（总量固定 + 已领集合）。
4. **完成是自动还是手动**？现在是手动点「完成任务」按钮。新结构下链式任务是否也自动检测完成？（用户只强调**终极挑战**必须硬性检测。）
5. **超出存储上限时怎么领**？窗口手动领仍可能一次领 500 木材而 cap 只有 100 —— 是"领了就夹取"，还是"必须留出空间才能领"，还是给一条"待领暂存"路径？
6. **应用范围**：主线任务 / 系统引导 / 科技树解锁三条线都要迁吗？**现有 4 个系统任务**是否并入新框架？
7. **教程的归属**：本设计明确"教程交给日志系统与手册"——但**项目现在完全没有教程机制**。所以本系统的落地**依赖日志/手册先补出教程能力**（这也是"日志系统大规模优化"的一个子项）。
8. **与日志重写的耦合**：本系统是日志系统重写**的一部分**，还是**之上**的一层？先有哪个？
9. **解锁负反馈的视觉**：`ui_kit` / `geo_icon` 是否够用（暗色 + 小锁 + 亮起 + 置顶的动画）？
