# v1.8.3 · 政事系统（数据 + 队列 + 征兵）

## 一、目标

建立一个**据点级的"政事"系统**：可以排队的事务 + 队列推进机制。**征兵作为第一条政事**。

> 这是**加玩法**，不是改界面——所以要先定义数据结构。

## 二、设计

### 政事的数据（建议新建 `scripts/data/decree_db.gd`）

每条政事至少需要：

| 字段 | 含义 |
| --- | --- |
| `id` | 唯一键（如 `recruit`） |
| `name` | 显示名（如「征兵」） |
| `desc` | 说明（一句话，UI 用） |
| `cost` | **消耗的行政点数**（跑条的目标值） |
| `require` | 前置条件（如需要训练场地 Lv.1、需要空闲人力） |
| `effect` | 完成时干什么（征兵 = 调用现有的征兵逻辑） |

### 队列与"跑条"

- **据点各自有一个政事队列**（本作只有首都一个据点，但结构上按据点存）。
- **推进机制**：每周期把**行政点数**积累进去；`progress >= cost` 即完成、执行 `effect`、出队。
- **与规划队列的区别**（UI 上并排显示，别混）：
  - **规划队列** = 建筑，消耗**生产力**（现有系统，不动）
  - **政事队列** = 政事，消耗**行政点数**（本段新增）

### 征兵作为第一条政事

把现有"征兵"（`GameState` 里那段"把空闲人力转成募集军"）**包装成一条政事**：效果照旧，但**入口从"管理页中控区"改成"排进政事队列"**。

### 三个设计决定（含理由）

| 决定 | 理由 |
| --- | --- |
| **抽出 `recruit_blocked_reason()`**，让"直接征兵"与"政事：征兵"共用一份判定 | 两处各写一遍的话，迟早一边改了另一边没改（本项目已经栽过好几次） |
| **政事执行失败 → 退还已投入的行政点数** | 攒够时前置可能已变（如首都驻满）。**不能白吞玩家的点数**；退款并记日志，玩家一眼看得懂 |
| **`SAVE_VERSION` 2 → 3** | 存档结构变了（据点多了 `decrees`）。按既有决策：1.0 期不做旧档兼容，版本不符**直接拒绝** |

### 两个坑

1. **我的疏漏**：把检查抽进 `recruit_blocked_reason()` 时，**顺手把 `var cap_key := ...` 也搬走了**，但函数体后面还在用它 → `Identifier "cap_key" not declared`。
   > 教训：**抽函数时"声明跟着走了、用处没跟着走"是最常见的漏**。抽完要通读调用方剩下的部分。
2. **环境机制**：新增 `class_name` 的文件后，**Godot 必须重扫项目**才会注册这个全局类（否则报 `Identifier "DecreeDB" not declared`）。
   > 做法：`godot --headless --path <项目> --import`，然后确认 `.godot/global_script_class_cache.cfg` 里有它。
   > **凡是"新建带 class_name 的脚本"，都要跟这一步。**
