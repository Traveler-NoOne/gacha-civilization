## 一、设想（用户原意）

**触发条件**：科技树攀完、能做的都做完了 —— 玩家**获得**一个**神秘按钮「成长」**。

> **⚠️ 这是设计的灵魂，不能写丢：按钮出现 ≠ 强制进入终局。要不要点「成长」，主动权在玩家手里，是玩家自己的选择。**
> 换句话说：**不点，游戏就一直照常玩下去**；是玩家**主动决定**"放手 / 飞升"。这份"自愿"本身就是主题 —— 家长是**决定**放手，而不是被逼退位（正好与结局三「你**决定**还是放手了」咬合）。
> 按钮名「成长」本身是**双关**：对玩家是"飞升成神"，对文明是"长大独立"。（用户特别强调过这一点。）

**点击之后**：

1. **玩家自身化生**为一个**属性非常高的终极威胁**（Boss 级单体）；
2. 玩家获得**数个带 CD（冷却）的技能**；
3. 玩家的**目标变了**：变成**占领目标的所有首都**；
4. **文明本身被 AI 决策树接管** —— 而且**每个都市的 AI 决策树是独立的**；
5. **每个高级单位也有独立 AI**；
6. 它们**竭尽全力去杀死玩家**。

**三种结局**：

| 结果 | 画面 |
| --- | --- |
| **AI 杀死了玩家**（它们赢了） | 结算画面，**最大的一行字**：**「他们长大了，不再需要一个全能的家长。」** |
| **玩家赢**（占领了所有首都） | 弹窗：**「你不放心他们，他们还没有长大。」** |
| **检测到玩家操作比较消极** | **「你决定还是放手了。」** |

**味道（为什么要这样设计）**：这是**「打得赢 = 坏结局」**的反转 —— 家长（玩家）如果放不下手、非要把孩子们按回去，说明它还没长大；被孩子们合力杀死，反而是**成长的证明**。这与本作"文明对自身行为的美化"的基调一致（全能的家长 vs 独立的孩子）。

## 二、主题参照（这个想法为什么"刺激"）

用户点名的三个参照，指向同一母题：**「庇护者必须放手，孩子必须亲手送走家长」**。而且三者恰好**一一对应三种结局**：

| 参照 | 那里的"家长" | 母题 | 对应本作的结局 |
| --- | --- | --- | --- |
| **星穹铁道 · 神主日** | 「家族」领袖，牧羊人式的爱 | 他为所有人造了一个**没有痛苦的美梦**，代价是**停滞**（永不醒来）；主角团反对的理由是"自由包含承受痛苦" | **玩家赢**（占完所有首都）：你把孩子留在"不需要长大的乐园"里 —— **温柔的暴政** →「你不放心他们，他们还没有长大。」 |
| **FGO · 提亚马特**（Beast II「回归之兽」） | 创世母神，真心爱着孩子 | 她的爱是**无差别的** —— 想把孩子拥回原点、永不分离；最终**被孩子们合力拒绝、送走** | **玩家被 AI 杀死**：孩子亲手送走母亲 →「他们长大了，不再需要一个全能的家长。」 |
| **原神 · 璃月 / 摩拉克斯** | 岩神，庇护璃月数千年 | 他主动**退位**，把璃月交给凡人（**神治 → 人治**），签下"终结一切契约的契约" | **消极**：不靠战斗，自己走下神坛 →「你决定还是放手了。」 |

**核心反转**：这三部作品里，玩家/主角都在**孩子**阵营（家长是对立面或退场者）；而本作让玩家**去演那个家长**。于是"打得赢"自然成了坏结局 —— 家长不肯放手，才需要被孩子亲手送走。**这才是"刺激"的来源。**

> **设计锚点（很重要）**：三个结局的关键其实**都不是"杀死玩家"** —— 提亚马特是被**"拒绝"**（而非单纯被消灭）、摩拉克斯是**自己退**。所以判定结局的核心不该是战斗胜负，而是**"你有没有放手"**。（注意：玩家化身既是"终极威胁"、也是"不肯退位的家长" —— 同一件事的两种说法。）

**可借的意象**（供落地时给化身技能 / 结局文本上色）：提亚马特的**回归 / 胎海**、神主日的**梦 / 秩序 / 牧羊**、摩拉克斯的**契约 / 磐岩 / 退位**。

## 三、与现有系统的关系（依赖分析）

### 可以复用的地基

| 复用点 | 位置 | 说明 |
| --- | --- | --- |
| 每周期流水线 | `GameState.end_cycle()` `game_state.gd:1441-1571`（带编号 1~11 段） | 文明 AI 每周期决策天然挂在这里（第 6 段是 `WorldGen.evolve`） |
| 世界演化 | `WorldGen.evolve()` `world_gen.gd:453-601` | 敌人行为目前是写死的随机脚本，可扩展成"按据点循环的 AI" |
| 单单位操作 | `move_unit()` `game_state.gd:741`、`unit_attack()` `:755`、行动点 `u["move_left"]` `:983` | 玩家化身可以直接走现成的移动/攻击 |
| 结算广播链 | `end_cycle()` 的 `report` → `on_cycle_finished(rep)`（`game_screen.gd:236-239`） | **结局检测与结算弹窗挂这里最省事**（可新增 `report["ending"]`） |
| 敌人破坏建筑 | `_damage_tile()` `world_gen.gd:610-651` | "终极威胁破坏建筑"已有实现，可被玩家化身复用 |

### 必须从零新建 / 现状缺口

| 缺口 | 现状（证据） |
| --- | --- |
| **敌方首都 / 多据点** | **没有**。只有我方一个首都：`state["capital"]`（`game_state.gd:49`）、`tile["is_capital"]`（`world_gen.gd:44`）、唯一一条 `sh_capital`（`game_state.gd:50,172-188`）。多据点只留了「切换据点」入口（`view_manage_page.gd:325-333`，注释"本作仅首都"）。敌方只有 `danger`（高危据点）/`threat`（终极威胁）/`wander`（游荡敌人）三种标记，**没有"首都"概念**。 |
| **「占领所有首都」的目标** | 依赖上一条 —— 得先有"敌方城市/首都"实体与多据点支持。 |
| **文明 AI 决策树** | **不存在**。现有敌人行为是 `evolve()` 里写死 + 随机。 |
| **每都市一棵独立 AI 树** | 依赖多据点；当前 `evolve()` 里没有"按据点分组"的循环。 |
| **高级单位的独立 AI** | 不存在。 |
| **技能与冷却（CD）** | **全项目零 CD 概念**（搜 `cooldown/冷却/cd` 零命中）。`UnitDB.UNIQUE_HOOKS`（`unit_db.gd:107-113`：`charge/pierce/guard_aura/volley/revive_once`）与 `u["skills"]` **只是展示用字符串**，只在角色页 UI 读（`character_page.gd:526-546, 558-574`），**战斗结算零引用**（`resolve_damage` `unit_db.gd:388-411`、`unit_attack`、`simulate_battle` 都不读）。 |
| **科技树"攀完"判定** | **没有**。`Consts.TECHS` 目前**只有 2 条**（`constants.gd:285-304`）；`state["techs"]` 记录已解锁（`game_state.gd:63`）。判据可简单用 `state["techs"].size() == Consts.TECHS.size()`。 |
| **玩家化身的生死语义** | 单位受伤致死在 `game_state.gd:799` 会**直接从 `state["units"]` 移除** —— 化身若走同一套，需要"阵亡即结局"的专门处理。 |
| **结局结算画面** | 不存在（现有弹窗是 `dialog_layer.gd`；"最大的一行字"需要专门的大字结算 UI）。 |

> 另一个注意点：`simulate_battle()`（`game_state.gd:1024-1098`，注释"抽象结算，替代战棋"）**实际只在测试里用**；运行时单单位攻击走 `unit_attack()`。"玩家 vs 一群单位"的战斗口径要定清楚（延续抽象结算，还是给化身单独一套）。

### 排期约束（结论）

**「成长模式」硬性排在 `多据点 + 敌方首都` 之后** —— 否则"占领所有首都""每都市一棵 AI 树"都无处落地。而多据点本身也是 v1.8 之后的事。所以这功能天然属于**游戏接近完成时的终局内容**。

## 四、待定问题（落地前必须拍板）

1. **化身的形态**：是"替换成一个终极威胁实体（会破坏建筑那种）"，还是"新增一个玩家 boss 单位"？落格是否需要新逻辑（地形通行当前不看单位，`tile_passable()` `game_state.gd:664`）？
2. **化身之后玩家还能操作什么**：原来的建造 / 征兵 / 抽卡 / 结束周期 UI 是否全部锁死，只留"单单位移动 + 攻击 + 技能"？（决定 UI 要藏多少）
3. **敌方首都从哪来**：终局时动态生成，还是地图上一直存在？几座？位置怎么定？
4. **「消极操作」的度量口径**：用"连续 N 周期不结束周期 / 不移动 / 不放技能"？还是用现成状态量（`stability()` `game_state.gd:407`、`happiness()` `:346`、`playtime` `:1535`）？阈值多少？
5. **结局触发优先级**：如果同一周期既"占完首都"又"被判定消极"，谁先？
6. **CD 技能具体是哪些**：是否直接对应现有 5 个 unique 接口（蓄力 / 贯穿 / 守护领域 / 齐射 / 不灭）？各自 CD 与效果？
7. **难度与"不做 rubber-band"的一致性**：项目明确**不做动态难度**（见主 README「设计理念与定位」）。文明 AI 是否也**固定强度**、不随玩家表现变强？
8. **平衡**：化身要多强才"打得赢也是坏结局"成立 —— 既不能强到玩家随便赢（那坏结局就成了唯一主动选择），也不能弱到必输（那"挣扎"没有意义）。
9. **能否反悔 / 按钮形态**：点了「成长」之后可否回退（读档 / 主动取消），还是不可逆？条件不满足时按钮是**隐藏**还是**置灰**？（注意：主动权在玩家手里，所以"按钮存在但不可点"与"根本不出现"是两种不同体验。）
10. **「成长」指谁**：按钮名双关 —— 要明确文案 / 提示在暗示哪一层（玩家**飞升** vs 放手让文明**长大**），这会决定按钮 tooltip 与触发时的语气。

## 五、落地时的建议切片（未定，仅供参考）

类似 v1.8 的做法，把终局拆成可独立验收的段：① 敌方首都/多据点 → ② 文明 AI 决策树（先单城）→ ③ 玩家化身 + 生死语义 → ④ CD 技能 → ⑤「成长」按钮与触发条件 → ⑥ 三种结局与结算画面 → ⑦ 圆角打磨与平衡。

> 每一步都要保持"游戏完整可玩"，并跑 `跑自检.bat`（12/12）。
