# v1.8 更新指导 · 索引

> v1.8 是**大世界（世界系统）的整体重写**：把世界升格为游戏底层（root），其余系统变成它上面的浮窗；同时重做地图绘制、点击语义、据点/建筑/科技/日志的入口，并加一个加载界面。
>
> **本目录的每一份 `v1.8.x.md` 就是一段可独立完成、可独立验收的工作。** 设计决定全部记在这里，**不依赖对话上下文**——所以任何一段都能隔很久之后再捡起来做。

## 一、总规则（每一段都必须遵守）

1. **每段结束必须是"游戏完整可玩"的状态。** 功能搬家时，**先把新家做好、再把旧入口删掉**；不允许出现"玩家暂时没法建造/没法征兵"的中间态。
2. **自检按需跑：用户要求时跑。** 跑时必须全绿（当前 **4 项**：`seed_check` / `fatal_check` / `popup_measure_check` / `dead_ref_check`）。
   **约 5 个版本以前的旧自检，直接清理掉、不要去改** —— 早期状态变化太大，改旧内容不如重新写。
   > 2026-10 用户改的第一版：以前是"每段都要跑 `跑自检.bat`"，改为**按需 + 低频**，不必每段都停下来等自检。
   > **2026-10-13 用户改的第二版**：项目数**只按 `tests/` 下实际存在的算**（不再引用 `15/15` 这种已失效的数字）；
   > 并且**旧测试是"清理重写"，不是"改预期"** —— 本条原来那句"结构变了就改测试的预期"**已作废**。
   > （理由出自 README「自动化验证」：*"对于大约 5 个版本以前的自检，进行清理，因为早期状态的改变太大，修改旧内容不如重新写。"*）
3. **每段结束提交一次 git**，提交信息形如 `v1.8.3 政事系统（数据 + 队列 + 征兵）`。
4. **改完就清死代码。** 删掉的入口/控件，其代码与美术一并处理，不留孤儿。
   > **清死代码的方法**：① 先**全项目** grep（**含 `tests/`** —— 那里最容易漏）；
   > ② 删完**必须真跑一遍自检** —— 平时那步"重扫语法"用的是 `--import`，它**不解析 `tests/` 下的脚本**，
   > 只有跑测试才抓得到"引用已删东西"的解析错（1.8.20.6 踩过：`mgr2` 在后面一节还在用）。
5. **每段的"验收"必须包含你自己的试玩确认**（不只自检绿）。
6. **「点哪弹哪」的浮窗，一律用 `UIKit.place_popup_at(p, gpos)`。** 不要自己写 position + 夹取 ——
   它一次处理完三件事：全局坐标（用 position 会在父节点原点不为 0 时整体偏掉）、
   尺寸要到下一帧才算准（会从旧位置向下长出屏幕）、下方放不下翻到点的上方。
   目前左键简约小窗、右键功能菜单都走它；以后再加任何"贴点弹出"的东西，也用这个。
   > **测试里凡是靠悬停弹出的镜头，必须先 `Input.warp_mouse(点)`** —— 截图是真窗口跑的，
   > 鼠标若在窗外会触发一次"移出地图"的悬停把弹窗收掉（v1.8.20.4 踩过）。
   > 第 2 条的补充：截图脚本 `_shoot()` 会**等到补间动画结束再拍**（v1.8.20.3 起），
   > 所以"连拍两遍应当一致、改动前后逐张比"是可信的。唯一例外是随机抽卡那张（17_dialog_draw）。

7. **注释写短：代码里只留"为什么不能那样写"（尤其反直觉的坑），来龙去脉写进 commit 信息。**
   > 1.8.20.10 由用户提出：注释太长会把代码淹掉，而"当初为什么要这么改"的价值在**历史**里
   > （`git log` / 更新指导段文件里都能查），不在一行代码旁边。

8. **地图按真实地理过程形成；参数只按"真实感"设，不为平衡而调。**
   玩法上的平衡，将来用**更多样的建筑 / 内容**去弥补（用户 2026-10 定的原则：本作要"更真实"而不是"更好玩"）。
   > 推论：地形/地貌的实现优先抄**真实过程**（噪声场、水流侵蚀…），阈值与系数只允许为了"像真的"而改；
   > 不要因为"海太多/山太少"这类**玩法**理由去调它。
9. **`docs/更新指导/` 里的段文件是"当时的记录"，不是"现在该怎么做的指令"**（2026-10-13 用户定）。
   过去版本的段文件**可以当作已经完成的内容** —— 它们是**更新历史的考古参考物**：
   里面出现的旧命令（`跑自检.bat`、`15/15`）与已删文件名**不要去"校正"**，那等于改写历史。
   **"现在该怎么验"只有一个出处**：下面这节。

### 现行验收方式（唯一出处）

1. **无头自检**（`--headless`，逐条跑）。**必须用「场景」跑，不能 `--script`** —— 后者不注册 autoload，测试会**假通过**：
   `seed_check` / `fatal_check` / `popup_measure_check` / `dead_ref_check` / `plate_check`
   > ⚠️ **跑的时候要带超时、并把输出落文件**（**别用会缓冲的管道**）：
   > 被测脚本或其依赖一旦有**解析错**（例如 `Cannot infer the type`），测试会打印半行后
   > **永远走不到 `quit()` → 静默挂死**，缓冲管道会让你连报错都看不到（2026-10-13 连踩两次）。
   > 另：**新建了带 `class_name` 的脚本后先跑一次 `--import`**，否则类名没注册。
2. **截图自检**（**非** headless；双击 `跑截图.bat`，或跑 `res://tests/screenshot.tscn`）：
   出图到 `tests/_shots/` 并生成 `00_MANIFEST.md`；观感逐张人看。
3. **像素验收用容差对比**（平均绝对差 MAD ≤ 2%；**不许用哈希相等**）—— 规矩与已知噪声清单见 `1.8.20.md`。
4. **观感 / 手感交给用户手测**（脚本能判的用脚本，观感只能人看）。
5. **每段一次 git 提交**。

> 补充（2026-10-13 踩出来的）：**带 `class_name` 的脚本从 git 恢复或新建之后**，
> 要先 `& $godot --headless --import --path <项目>`，否则全局类名没注册、依赖它的脚本编译失败，
> 表现常常是"某函数不存在"甚至**看门狗超时**（不是崩溃，最难认）。

### 术语

- **跑条**：进度条。**政事队列** = 每周期把**行政点数**积累进去，条满即完成（与现有规划队列同一手感）。

## 四、为什么是这个顺序

- **绘制（1）最前**：独立，且修掉现存 bug；世界升格后它是最底层的代码，先弄干净。
- **政事（3）在窗口（4）之前**：窗口下半段要显示政事队列，得先有政事。
- **布局（7）在功能搬家（3~6）之后**：删入口前，功能必须都有新家。
- **世界升格（8）在布局稳定之后**：它动的是"谁在底层"这件事，前面的浮窗都定型了才不返工。
- **加载界面（9）最后**：它要"包"住最终流程，流程没定就包不住。
