> 状态：⬜ 进行中
> 模式：**助理代做**（用户原话：*"我这个总是东问西问的小白是做不了这么重量级的更新的，因此只能你来做了"*）
> 版本号的来历：用户定 **1.8.20** —— *"实装分辨率系统说到底和 UI 系统是一个东西，因此本质上没脱离 1.8 是更新 UI 系统的点；但又重大到确实值得跨越一个比较大的版本数量，作为仪式感。"*

## 一、要解决的问题

**分辨率设置是假的。** 现状（`project.godot`）：

```
window/size/viewport_width=1280              ← 基准画布固定 1280×720
window/size/viewport_height=720
window/stretch/mode="canvas_items"           ← 整个 UI 先画在 1280×720 上，再整体缩放
window/stretch/aspect="expand"
```

两条独立的问题：

1. **它只是个"缩放"**：`canvas_items` 让 UI 永远按 1280×720 排版再等比拉伸 → 选 1920×1080 的唯一效果是"所有东西一起变大"，
   不是"多出空间、UI 更精细"。玩家看不出区别（1080p 屏上跟最大化窗口一样）。
2. **它不持久化**：`DisplayServer.window_set_size(...)` 只改这次运行，重启回到 1280×720。

用户在 **v1.2 时期**就发现了，一直压着没修（*"我觉得这个问题还不重要"*）；
v1.8 大更完 UI、又重置了设置系统之后，时机到了。

**代价**（用户原话）：*"一旦要实装，整个 UI 系统的实现都要重置，还要加上一堆和分辨率系统实装后搭配的 UI 大小词典。"*

## 二、三条设计决定（助理定，用户可否决）

| 项 | 定案 | 理由 |
| --- | --- | --- |
| 目标分辨率 | **1280×720 / 1600×900 / 1920×1080 / 2560×1440** | 覆盖常见屏；四档对应 1.0 / 1.25 / 1.5 / 2.0 倍 |
| 窗口是否可自由缩放 | **锁定**（不可拖边） | "大小词典"天然离散；自由缩放会出现 1280×913 这类中间态，要么半破要么等于回到自动缩放 |
| 改完何时生效 | **下次启动生效** | 与 12-C 的"方案 A"一致（设置只存、不即时应用）；工作量可控 |

## 三、技术路线

1. **新增 `UI` 尺寸词典（Autoload，名 `UI`）** —— `scripts/core/ui_scale.gd`
   - `UI.scale`：当前档位的倍率（1.0 / 1.25 / 1.5 / 2.0）
   - `UI.px(n)`：把"按 1280×720 设计"的像素值换算到当前档
   - `UI.fs(n)`：字号同理
   - `UI.resolutions()` / `UI.set_resolution(size)` / `UI.current_resolution()`
   - ⚠️ 与 `UIKit` **不是一回事**：`UIKit` 是静态控件工厂，`UI` 只提供尺寸来源。命名容易混，所以在文件头写清楚。
2. **分辨率持久化**（`AppSettings`）：加 `resolution` 项，落到 `user://settings.cfg`（和作弊开关、自动存档周期同一处）。
3. **启动时应用**：`main.gd` 起来时 `UI.set_resolution(AppSettings.resolution())` + `DisplayServer.window_set_size(...)`；
   同时关掉自动拉伸（`stretch/mode` → `disabled`），让 UI 按**真实像素**排版。
4. **写死的尺寸全部改走 `UI.px()` / `UI.fs()`** —— 这是工作量主体（全项目 `custom_minimum_size` 约 40 处、
   `add_theme_font_size_override` 几十处，还有各种 `position = Vector2(72, 64)`）。

## 五、风险与注意

## 1.8.20-B 完成记录（换地基）

### 做了什么

- `project.godot`：`window/stretch/mode` 由 `canvas_items` → **`disabled`** —— UI 从此按**真实像素**排版。
- `dialog_layer.gd`：
  - `fit_now()` 对**退化视口**兜底：`vh < 200` 时改用**设计基准高度**（`UI.current_size().y`）。
    理由：窗口已锁死在真实分辨率档位，"视口小得离谱"只可能出现在无头/退化环境（实测 headless 只有 64 高）。
  - 新增 `usable_height()` —— 把"弹窗自己认定的可用高度"暴露出来，供自检判断"按钮是否在可用区域内"。
- `diag_cheat_mouse`：参照物从真实视口改成 `dlg.usable_height()`。实测：弹窗 539 高、视口认作 720、
  「摧毁全部敌对单位」在可用区域内 = true。

### 验收（这一段连验收方法本身都改了）

原打算用**截图逐张哈希相等**当铁证 —— **结果这个方法本身是错的**：
实测**同一个状态连拍两次，42 张里就有 15 张哈希不同**（渲染不是字节级确定的，抗锯齿/字体栅格有细微抖动）。
差一点把噪声当成"关掉拉伸改变了渲染"报上去。

改用**容差像素对比**（PIL 算平均绝对差 MAD）：新图 vs 基线，**42 张里只有 1 张超过 1%**：

- `17_dialog_draw` **5.04%** —— 它是**抽卡结果弹窗**，卡是随机的（测试没给它固定种子），
  **每次跑都不一样是它自带的**，与本改动无关。
- 其余 41 张全部 **≤ 0.31%** —— 抗锯齿噪点级别。

→ 结论：**关掉自动拉伸没有改变任何排版**，"换地基没搬家"成立。

### 踩的坑（都写进 project.godot 备忘与注释了）

1. **别用"整块替换"改 `project.godot`**：上一次这么干，把两行真设置连同注释一起写坏了
   （注释被并成一行、多出垃圾键）。改用**精确编辑**，并且**改完立刻 `git diff` 核对**。
2. **无头环境的视口只有 64 高**，而且两条路都不通：
   - `DisplayServer.window_set_size(...)` 在 headless 下**无效**；
   - `get_window().size = Vector2i(1280,720)` **直接把测试挂死**（实测 TIMEOUT）。
   → 正确做法：让被测对象（`dialog_layer`）**自己认定可用尺寸**并暴露出来，测试问它，而不是问真实视口。
3. **PowerShell 的 here-string 结尾不带换行**：拿它替换"带换行结尾"的文本块时，
   后一行会被吞进前一行（这次把一句 `await get_tree().process_frame` 并进了注释里）。
   替换块结尾要**显式补一个换行**。

## 验收规则（像素对比怎么用才对）

这一段靠**截图容差对比**验收（`UI.px/fs` 在 1.0 档数值不变 → 视觉应当无变化）。踩过的坑与定下的规矩：

### 规矩

1. **不许用哈希相等**：渲染不是字节级确定的（同一状态连拍两次，42 张里就有 15 张哈希不同）。
   用 PIL 算**平均绝对差（MAD）**，阈值 **2%**。
2. **对比基线要在"改动前、同一份代码"上拍**（连拍两次取噪声带），不要拿很久以前的图比。
3. **改动前先量噪声带**：本次实测——绝大多数 ≤ 0.5%；`02c_dialog_feedback`/`20_unit_panel` 偶尔到 0.5%；
   `19_dialog_cheat` 抖动最大到 **1.5%**（离群）。
4. **容差结果要当提交门槛**（不能只看自检 15/15 就提交 —— 我第一次就是这么漏过去的）。

### 已知噪声清单（内容自变，与本段改动无关）

| 图 | 抖动 | 原因 |
| --- | --- | --- |
| `17_dialog_draw` | **≈ 5%** | 抽卡结果弹窗：卡是随机的（截图自检原本没给抽卡定种） |
| `19_dialog_cheat` | 0.1 ~ 1.5% | 作弊菜单列的是**随机生成的敌人** |

**已做的缓解**：截图自检开跑时 `seed(20240607)` + `GameState._rng.seed = 20240607`，
把全局 RNG 与 GameState 的 RNG 都定种（原来 `GameState._rng` 是 `randomize()` 的）。
仍未定的两处（会留着当已知噪声）：**时间戳生成的 uid**（`Time.get_ticks_usec()`）与**抽卡视图自己的 rng**。
