# 1.8.20 · 实装分辨率系统（重量级）

> 状态：⬜ 进行中
> 模式：**助理代做**（用户原话：*"我这个总是东问西问的小白是做不了这么重量级的更新的，因此只能你来做了"*）
> 版本号的来历：用户定 **1.8.20** —— *"实装分辨率系统说到底和 UI 系统是一个东西，因此本质上没脱离 1.8 是更新 UI 系统的点；但又重大到确实值得跨越一个比较大的版本数量，作为仪式感。"*

## 一、要解决的问题

**分辨率设置是假的。** 现状（`project.godot`）：

```
window/size/viewport_width=1280              ← 基准画布固定 1280×720
window/size/viewport_height=720
window/stretch/mode="canvas_items"           ← 整个 UI 先画在 1280×720 上，再整体缩放
window/stretch/aspect="expand"
```

两条独立的问题：

1. **它只是个"缩放"**：`canvas_items` 让 UI 永远按 1280×720 排版再等比拉伸 → 选 1920×1080 的唯一效果是"所有东西一起变大"，
   不是"多出空间、UI 更精细"。玩家看不出区别（1080p 屏上跟最大化窗口一样）。
2. **它不持久化**：`DisplayServer.window_set_size(...)` 只改这次运行，重启回到 1280×720。

用户在 **v1.2 时期**就发现了，一直压着没修（*"我觉得这个问题还不重要"*）；
v1.8 大更完 UI、又重置了设置系统之后，时机到了。

**代价**（用户原话）：*"一旦要实装，整个 UI 系统的实现都要重置，还要加上一堆和分辨率系统实装后搭配的 UI 大小词典。"*

## 二、三条设计决定（助理定，用户可否决）

| 项 | 定案 | 理由 |
| --- | --- | --- |
| 目标分辨率 | **1280×720 / 1600×900 / 1920×1080 / 2560×1440** | 覆盖常见屏；四档对应 1.0 / 1.25 / 1.5 / 2.0 倍 |
| 窗口是否可自由缩放 | **锁定**（不可拖边） | "大小词典"天然离散；自由缩放会出现 1280×913 这类中间态，要么半破要么等于回到自动缩放 |
| 改完何时生效 | **下次启动生效** | 与 12-C 的"方案 A"一致（设置只存、不即时应用）；工作量可控 |

## 三、技术路线

1. **新增 `UI` 尺寸词典（Autoload，名 `UI`）** —— `scripts/core/ui_scale.gd`
   - `UI.scale`：当前档位的倍率（1.0 / 1.25 / 1.5 / 2.0）
   - `UI.px(n)`：把"按 1280×720 设计"的像素值换算到当前档
   - `UI.fs(n)`：字号同理
   - `UI.resolutions()` / `UI.set_resolution(size)` / `UI.current_resolution()`
   - ⚠️ 与 `UIKit` **不是一回事**：`UIKit` 是静态控件工厂，`UI` 只提供尺寸来源。命名容易混，所以在文件头写清楚。
2. **分辨率持久化**（`AppSettings`）：加 `resolution` 项，落到 `user://settings.cfg`（和作弊开关、自动存档周期同一处）。
3. **启动时应用**：`main.gd` 起来时 `UI.set_resolution(AppSettings.resolution())` + `DisplayServer.window_set_size(...)`；
   同时关掉自动拉伸（`stretch/mode` → `disabled`），让 UI 按**真实像素**排版。
4. **写死的尺寸全部改走 `UI.px()` / `UI.fs()`** —— 这是工作量主体（全项目 `custom_minimum_size` 约 40 处、
   `add_theme_font_size_override` 几十处，还有各种 `position = Vector2(72, 64)`）。

## 四、子步骤（都在 1.8.20 这一段里；每个子步骤单独提交）

### 1.8.20-A 骨架与持久化（**不改观感**）

- 设置弹窗：分辨率改成"改完提示**下次启动生效**"

- 验收：自检 15/15；截图 42 张在 **1280×720** 下**逐张与原图一致**（这是"换地基没搬家"的证据）

## 五、风险与注意

- **测试都按 1280×720 跑**：截图自检里 `DisplayServer.window_set_size(1280, 720)` 是**程序化**设的，
  即使窗口锁成不可缩放也照样生效（程序化不受 `resizable` 限制），所以测试不受影响 —— 但要**实测确认**。
- **地图六边形几何**：`hex_map_view` 的绘制依赖画布尺寸，换分辨率后要逐档看图确认没破。
- **`_place_floating_ui` / 对话框定位**：已经用 `size` / `get_viewport_rect()` 算，属于"本来就自适应"的一类，优先检查它们没被写死值坑到。
- **加载界面 / 主菜单**里有绝对坐标（`Vector2(72, 64)`、`Vector2(-110, -56)`），是重点排查对象。
- **顺手待查（不在本段混改）**：`AppSettings` 自己有 `autosave_interval()/set_autosave_interval()`，
  而设置弹窗用的是 `GameState` 的同名函数 —— 疑似两套并存，回头单独查。

## 六、验收（整段）

1. 四档分辨率下都能启动、能玩、UI 不破版。
2. 选择的分辨率**重启后仍然生效**（持久化）。
3. 分辨率不再是"整体缩放"：1920×1080 下 UI 元素**尺寸合理**（不是把 720p 拉伸 1.5 倍那种糊）。
4. `跑自检.bat` 全绿；`跑截图.bat` 每档都能出图、清单同步。
